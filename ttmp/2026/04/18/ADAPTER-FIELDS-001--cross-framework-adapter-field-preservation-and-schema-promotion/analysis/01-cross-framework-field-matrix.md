# Cross-framework field matrix

## Goal

Record, in one place, how Pi, Codex, and Claude Code represent the candidate adapter/schema fields discussed during the schema-gap review, and distinguish between:

- fields that are actually present in raw source data
- fields that are absent in one or more frameworks
- fields already preserved in minitrace
- fields that should be promoted now versus preserved only in metadata

## Quick conclusions

### Promote now

1. `tool_calls[].output.exit_code`
2. `tool_calls[].input.justification`

### Preserve in metadata first

- Codex: `approval_policy`, `sandbox_policy`, `collaboration_mode`, `truncation_policy`, `rate_limits`, `turn_id`, `phase`, `memory_citation`, command `source`, `parsed_cmd`, `stdout`, `stderr`
- Claude Code: `caller`, `entrypoint`, `stop_reason`, `stop_sequence`, `slug`, `parentUuid`, `isSidechain`, cache bucket details
- Pi: `details.diff`, assistant `stopReason`, assistant `errorMessage`

### Do not promote yet

- normalized sandbox enum/policy model
- `stdout` / `stderr` as first-class schema fields
- thread/tree modeling from Claude `parentUuid` / `isSidechain`
- heuristic error categories

## Per-framework notes

### Codex

What Codex is best at exposing:

- command execution detail (`exit_code`, `stdout`, `stderr`, `parsed_cmd`, command `source`)
- policy/runtime context (`approval_policy`, `sandbox_policy`, `collaboration_mode`, `truncation_policy`)
- event-level context (`turn_id`, `phase`, `memory_citation`, `rate_limits`)

What is weak or absent in the sampled raw data:

- no Claude-style thread metadata
- no Pi-style edit diff payloads
- no observed `justification` in local sampled raw sessions, even though adapter fixtures already support it in session-jsonl-v1 arguments

### Claude Code

What Claude is best at exposing:

- tool-use metadata (`caller`)
- session/thread metadata (`entrypoint`, `slug`, `parentUuid`, `isSidechain`)
- turn termination and usage metadata (`stop_reason`, `stop_sequence`, cache bucket split)

What is weak or absent in the sampled raw data:

- no native numeric `exit_code`
- no separate `stdout` / `stderr`
- no Pi-style edit diff payloads

### Pi

What Pi is best at exposing:

- tool-result status and error semantics via message-level `toolResult` + `isError`
- edit diff payloads (`details.diff`)
- assistant termination/error detail (`stopReason`, `errorMessage`)

What is weak or absent in the sampled raw data:

- no numeric command `exit_code`
- no `justification`
- no structured sandbox/approval policy comparable to Codex
- no Claude-style thread/session metadata

## Recommended implementation order

1. Add first-class schema support for `tool_calls[].output.exit_code`.
2. Add first-class schema support for `tool_calls[].input.justification`.
3. Update the Codex adapter to populate both fields across the supported parser paths.
4. Add regression coverage for both fields.
5. In a later slice, preserve the metadata-only fields above without promoting them immediately.

## Evidence caveats

- The sampled Codex sessions clearly prove `exit_code` and the policy/runtime metadata fields.
- The sampled Codex sessions did **not** contain a live `justification` example; that field is currently justified by adapter/test coverage and known session-jsonl-v1 argument structure rather than by a local raw-session hit.
- The Claude conclusions are based on one real JSONL transcript plus the current adapter behavior.
- The Pi conclusions are based on the real Jellyfin session that originally exposed the `toolResult.isError` bug.
