## 1. Overview

### What is this feature?

The ANNOTATE-CLI feature adds the ability to attach **human-authored metadata** ("annotations") to minitrace session files. A minitrace session is a `.minitrace.json` file that records an AI agent conversation — its turns, tool calls, errors, and outcomes.

Annotations let users label interesting moments: AI failures, user errors, environment issues, patterns worth noting, questions to investigate. They support a taxonomy of failure codes (Minitrace F-codes, MAST, ToolEmu), optional classification levels (public → customer-confidential), and tagging.

### Why does it exist?

Before this feature:
- Annotations could only exist inside `.minitrace.json` files as a JSON array
- No CLI or web UI could create, edit, or query annotations
- DuckDB loaded sessions into an in-memory temp table (read-only) — no writes possible

After this feature:
- A SQLite database (`annotations.db`) serves as the **working store** for all annotation operations
- A CLI (`go-minitrace annotate add/list/edit/delete/sync/import`) handles all annotation CRUD
- An HTTP API (served by `go-minitrace serve`) exposes CRUD endpoints for the web UI
- DuckDB queries annotations **live** via its `sqlite_scanner` extension — no refresh needed after writes
- Annotations are written back to `.minitrace.json` only via explicit `sync` command

### The core tension this feature resolves

DuckDB is excellent for **reading** structured data but poor for **writing** it back. `.minitrace.json` files are the portable interchange format but are slow to parse/serialize per annotation.

**Solution:** SQLite as the working store (fast OLTP writes), DuckDB for live analytical queries, `.minitrace.json` files as the authoritative source modified only via explicit sync.

## 2. What Was Built

### Storage layer: `pkg/annotate/store.go`

A SQLite database at `outputDir/annotations.db` with two tables:

**`annotations`** — the main annotation table:

| Column | Type | Notes |
|--------|------|-------|
| `id` | TEXT PK | UUID generated by caller |
| `session_id` | TEXT | which session this annotation belongs to |
| `annotator` | TEXT | who created it ("user", "model", etc.) |
| `scope_type` | TEXT | `session`, `turn`, or `tool_call` |
| `target_id` | TEXT | what it's attached to |
| `category` | TEXT | `ai-failure`, `user-error`, etc. |
| `title` | TEXT | short description |
| `detail` | TEXT | freeform notes |
| `tags` | TEXT | JSON array of strings |
| `taxonomy_m` | TEXT | JSON array — Minitrace codes |
| `taxonomy_mast` | TEXT | JSON array — MAST codes |
| `taxonomy_tm` | TEXT | JSON array — ToolEmu codes |
| `classification` | TEXT | nullable — `public`, `internal`, etc. |
| `created_at` | TEXT | ISO 8601 UTC |
| `updated_at` | TEXT | ISO 8601 UTC |

**`sync_state`** — tracks which sessions have unsynced changes:

| Column | Type | Notes |
|--------|------|-------|
| `session_id` | TEXT PK | |
| `synced_at` | TEXT | ISO 8601 UTC, empty string = never synced |
| `change_count` | INTEGER | increments on every mutation |

Indexes: `(session_id)`, `(scope_type, target_id)`, `(category)`, `(annotator)`.

SQLite opened in **WAL mode** with `busy_timeout=5000` for concurrent reader + serialized writer access.

### Sync layer: `pkg/annotate/sync.go`

The sync module writes annotations from SQLite back to `.minitrace.json` files. Key behavior:

- **Atomic writes**: writes to `{file}.tmp` then `os.Rename` — crash-safe on POSIX same-filesystem
- **Generic JSON patching**: unmarshals into `map[string]any`, replaces the `annotations` key, re-marshals — avoids re-serializing the entire session
- **Nil → empty array**: `nil` annotations become `"annotations": []` not `"annotations": null`
- **`DryRun` mode**: prints what would happen without modifying files
- **`SyncAll`**: iterates over `sync_state`, fetches annotations per session, writes each file, calls `markSynced`

### DuckDB integration: `pkg/annotate/duckdb.go`

Attaches the SQLite database directly into DuckDB's query engine via the built-in `sqlite_scanner` extension:

```sql
INSTALL sqlite_scanner;
LOAD sqlite_scanner;
CALL sqlite_attach('/abs/path/to/annotations.db', overwrite => true);
SELECT * FROM annotations;  -- live, no refresh needed
```

**Key facts:**
- `sqlite_scanner` is built into DuckDB — no CGO, no external dependency
- Named parameter syntax `overwrite => true` is **required** — positional booleans cause a Binder Error
- Attached SQLite tables land in `main` schema — no schema prefix needed
- Annotations are **live**: DuckDB re-reads the SQLite file on every query. No refresh step after writes.

## 3. Architecture Decisions

### Why SQLite instead of DuckDB for the working store?

DuckDB is an **analytical engine** (OLAP). It excels at reading and aggregating large datasets but is not designed for high-frequency single-row writes. Critically, DuckDB has no mechanism to write back to individual JSON files — `COPY TO` writes one file per invocation, and there's no way to "update the annotations array in session X" without Go code.

SQLite is an **OLTP engine**. Fast single-row inserts, ACID transactions, WAL mode for concurrent readers, human-inspectable with the `sqlite3` CLI.

### Why two storage formats (SQLite + JSON)?

`.minitrace.json` files are the **canonical interchange format**. They are portable, version-controllable, and shareable. SQLite is the **working store** optimized for write performance and queryability.

The sync step (explicit `annotate sync`) is intentional: it gives users control over when the authoritative JSON files are modified. This follows the principle that data should be immutable until an explicit export step.

### Why DuckDB `sqlite_scanner` instead of JSON export/import?

The original design called for exporting annotations to JSON and loading into DuckDB as a temp table. This approach has two problems:

1. **Stale data**: you'd need to re-export on every write to see new annotations
2. **Double storage**: annotations live in SQLite AND in a JSON file

`sqlite_scanner` solves both: it attaches the SQLite file directly into DuckDB, so queries are always live. No export, no refresh, no duplication.

The critical syntax is `CALL sqlite_attach($1, overwrite => true)` — **named parameter required**. DuckDB treats a positional boolean as a table name, causing a Binder Error.

### Why a separate `sync_state` table?

The sync step needs to know which sessions have been modified since the last successful sync. Rather than scanning all annotation records, `sync_state` provides an O(1) lookup per session. The `markUnsynced` trigger runs on every INSERT/UPDATE/DELETE to increment the change counter.

### Why `map[string]any` for JSON patching in `SyncSession`?

A naive approach would be: unmarshal to `minitrace.Session`, modify `Session.Annotations`, re-marshal. This loses formatting, comments, and any non-standard fields in the JSON.

By unmarshaling to `map[string]any`, we preserve every field in the file and only replace the `annotations` key. Re-marshaling with `MarshalIndent` produces clean 2-space-indented output.

### Why `--output-dir` as the primary path?

The SQLite database lives at `outputDir/annotations.db`, colocated with the sessions it annotates. This keeps annotations with their data and makes it clear which DB owns which sessions.

The `sync` command infers the archive glob from the output dir: `<output-dir>/active/*/*.minitrace.json`. This assumes the standard output layout — if not, users specify `--archive-glob` explicitly.

## 4. Implementation Walkthrough

### Step 1: SQLite store (`pkg/annotate/store.go`, commit `238aba7`)

The foundation. `Open(ctx, outputDir)` resolves to absolute path, creates the directory, opens SQLite with WAL pragma, runs `migrate()`. `migrate()` runs `CREATE TABLE IF NOT EXISTS` for both tables plus indexes.

Key functions:
- `AddAnnotation`: inserts annotation, JSON-encodes tags and taxonomy columns, calls `markUnsynced`
- `GetAnnotationsForSession`: selects + JSON-decodes tags/taxonomy
- `List`: dynamic WHERE builder with `LIKE` across all 3 taxonomy columns for substring matching
- `Update`: `buildPatchSET` helper walks non-nil `AnnotationPatch` fields, builds `SET col = ?, col = ?` dynamically
- `Delete`: lookups session_id before deleting, then calls `markUnsynced`
- `markUnsynced`: UPDATE then INSERT (two-step because SQLite VALUES restriction blocks `ON CONFLICT DO UPDATE` referencing column values)
- `markSynced`: `INSERT ... ON CONFLICT DO UPDATE` (this works because `excluded.` prefix is used)

### Step 2: Sync module (`pkg/annotate/sync.go`, commit `6c71f31`)

`SyncSession(filePath, annotations, opts)`:
1. Read file → `os.ReadFile`
2. Unmarshal to `map[string]any`
3. Replace `annotations` key (nil → `[]any{}`, else serialize each annotation individually)
4. `MarshalIndent` → append `\n`
5. If `DryRun`: print and return
6. Else: `WriteFile(tmp)`, `Rename(tmp, file)`

`SyncAll(ctx, sessionIndex, opts)`:
1. Get unsynced sessions from store (or single session if `opts.SessionID`)
2. For each: lookup file path from `sessionIndex`, fetch annotations, call `SyncSession`
3. On success: `markSynced`
4. Aggregate results into `SyncReport`

### Step 3: CLI commands (commit `eec4611`)

- **Shared helpers** in `root.go`: `openStore(cmd)`, `closeStore`, `parseCommaList`, `flagIsSet`
- **`add.go`**: validates category against known set, generates UUID + timestamp, calls `store.AddAnnotation`
- **`list.go`**: calls `store.List`, renders table (`tabwriter`) or JSON
- **`edit.go`**: `flagIsSet` walks `cmd.Flags()` to detect which flags were explicitly set — only those fields go into `AnnotationPatch`
- **`synccmd.go`**: infers glob as `<output-dir>/active/*/*.minitrace.json`, calls `ExpandArchiveGlobs`, builds session index from file contents, calls `store.SyncAll`
- **`import.go`**: reads JSON file/stdin, converts to `[]Annotation`, calls `AddAnnotation` per item

### Step 4: DuckDB integration (commit `4116a58`)

`AttachAnnotationsToDuckDB(conn, outputDir)`:
1. `INSTALL sqlite_scanner`
2. `LOAD sqlite_scanner`
3. Resolve `outputDir/annotations.db`
4. `os.Stat` — if file doesn't exist, skip (DB created on first write)
5. `CALL sqlite_attach($1, overwrite => true)` — named parameter required

Wired into `serve.go` between `OpenConnection` and `LoadArchive`. Errors are logged as warnings — non-fatal.

The `outputDirFromGlobs` helper expands the archive glob to actual file paths, then takes `filepath.Dir(filepath.Dir(firstFile))` to get the output root.

Updated `queries/annotations.sql` to `JOIN annotations a ON sb.id = a.session_id` instead of `UNNEST(annotations)`.

### Step 5: HTTP API (commit `f155b6e`)

Six handlers in `handlers_annotations.go`. Route registration in `server.go`. `NewServer` signature updated to accept `annoStore` and `annoIndex`.

The `CreateAnnotationRequest` type decouples the HTTP body from the internal Go type (HTTP uses snake_case JSON, Go uses PascalCase). `handleUpdateAnnotation` uses type assertions to extract typed values from `map[string]any`.

**Serve wiring (commit `2e15017`):** `annotate.Open(signalCtx, outputDir)` called after `AttachAnnotationsToDuckDB`, result passed to `NewServer`. Store closed via `defer`.

### Step 6: Web UI (commit `7421127`)

RTK Query provides automatic caching and invalidation. `createAnnotation` and `deleteAnnotation` invalidate the `Annotations` tag for the specific session ID, causing `useGetSessionAnnotationsQuery` to re-fetch automatically.

## 6. Lessons Learned

### SQLite ON CONFLICT VALUES restriction

SQLite does not allow referencing a column in the `VALUES` clause of an `INSERT ... ON CONFLICT DO UPDATE` statement. The error message ("no such column") is misleading — it suggests a typo rather than a documented restriction. Workaround: separate `UPDATE` then `INSERT`.

### DuckDB named parameters for boolean flags

DuckDB's prepared statement system treats positional arguments as data values, not flags. The `sqlite_attach` function's `overwrite` parameter must be passed as a **named parameter** (`overwrite => true`), not positional (`true`). The error for positional arguments is a Binder Error, not a clear "named parameter required" message.

### Shell function return values

In bash, a function cannot directly return a value. Returning `RESP=$(curl ...)` inside a function makes `RESP` local to the function's scope. To capture both body and HTTP code, use global variables (`_BODY`, `_CODE`) or write to a temp file.

### gofmt and map literal alignment

When all values in a map literal are the same length, gofmt aligns the RHS to the same column. `"observation"` is 11 chars, so gofmt aligns `true` at column 22 (with one space), while `"user-error"` (9 chars) gets two spaces. `gofmt -w` normalizes this.

### `json.Unmarshal` nil slice behavior

`var out []string` creates a nil slice. `json.Unmarshal([]byte("[]"), &out)` does NOT append anything — the result is still nil. For both `null` and `[]`, `Unmarshal` leaves the destination nil. Explicit `"[]"` checking is needed.

### Always audit `git status` after a complex implementation

Multiple commits were made during this session. A late `git status` revealed that `serve.go` wiring changes were staged but uncommitted. Always run `git status --short` and `git log --oneline -n` at the end of a session to verify all changes are captured.

## 7. For the Intern: System Guide

### How a minitrace session is structured

A `.minitrace.json` file represents a single AI agent session. Here's the top-level structure:

```json
{
  "id": "uuid-here",
  "schema_version": "0.2.0",
  "profile": "organic",
  "title": "Fix authentication bug",
  "classification": "internal",
  "annotations": [],  ← this is what we annotate
  "turns": [...],
  "tool_calls": [...],
  "metrics": {...}
}
```

The `annotations` array is an array of `Annotation` objects with this structure:

```json
{
  "id": "uuid-of-annotation",
  "timestamp": "2026-04-04T00:00:00Z",
  "annotator": "user",
  "scope": { "type": "session", "target_id": "uuid-of-session" },
  "content": {
    "category": "ai-failure",
    "tags": ["auth", "regression"],
    "title": "Authentication failure in tool call",
    "detail": "The agent called the API without the auth header"
  },
  "taxonomy_mappings": {
    "minitrace": ["F-AUT"],
    "mast": [],
    "toolemu": []
  },
  "classification": "internal"
}
```

### API reference

#### CLI

```bash
# Add annotation
go-minitrace annotate add \
  --output-dir ./output \
  --session sess-001 \
  --category ai-failure \
  --title "Auth header missing" \
  --detail "The agent didn't include the Authorization header" \
  --tags auth,regression \
  --taxonomy-minitrace F-AUT

# List all annotations (table format)
go-minitrace annotate list --output-dir ./output

# List as JSON
go-minitrace annotate list --output-dir ./output --format json

# List with filters
go-minitrace annotate list --output-dir ./output --category ai-failure --limit 20

# Edit (only title will change — other fields untouched)
go-minitrace annotate edit --id <ann-uuid> --title "Updated title"

# Delete
go-minitrace annotate delete --id <ann-uuid>

# Sync all unsynced sessions back to JSON
go-minitrace annotate sync --output-dir ./output

# Sync single session (dry run)
go-minitrace annotate sync --output-dir ./output --session sess-001 --dry-run

# Import from JSON
go-minitrace annotate import --file annotations.json --output-dir ./output
```

#### HTTP API (when serve is running)

```bash
BASE=http://localhost:8080/api

# List annotations for a session
curl $BASE/sessions/sess-001/annotations

# Create annotation
curl -X POST $BASE/sessions/sess-001/annotations \
  -H 'Content-Type: application/json' \
  -d '{
    "category": "ai-failure",
    "title": "API called without auth",
    "detail": "The WriteFile tool was called without checking auth",
    "tags": ["auth"],
    "annotator": "user"
  }'

# List all annotations (with filters)
curl "$BASE/annotations?category=ai-failure&annotator=user&limit=10"

# Patch annotation
curl -X PUT $BASE/annotations/<ann-uuid> \
  -H 'Content-Type: application/json' \
  -d '{"title": "Updated title", "classification": "internal"}'

# Delete annotation
curl -X DELETE $BASE/annotations/<ann-uuid>

# Sync SQLite → JSON (all sessions)
curl -X POST $BASE/annotations/sync

# Sync single session (dry run)
curl -X POST $BASE/annotations/sync \
  -H 'Content-Type: application/json' \
  -d '{"session_id": "sess-001", "dry_run": true}'
```

#### DuckDB (live queries via sqlite_scanner)

```sql
-- Start DuckDB with the analysis.duckdb that serve created
duckdb analysis.duckdb

-- Attach annotations (serve does this automatically)
INSTALL sqlite_scanner;
LOAD sqlite_scanner;
CALL sqlite_attach('/path/to/output/annotations.db', overwrite => true);

-- Count annotations per category
SELECT category, COUNT(*) AS n
FROM annotations
GROUP BY category
ORDER BY n DESC;

-- Join annotations with session data
SELECT
    a.session_id,
    sb.environment->>'agent_framework' AS framework,
    a.category,
    a.title,
    a.taxonomy_m AS taxonomy_minitrace
FROM annotations a
JOIN sessions_base sb ON sb.id = a.session_id
WHERE a.category = 'ai-failure'
ORDER BY a.created_at DESC;

-- All sessions annotated by a specific user
SELECT DISTINCT a.session_id, sb.title
FROM annotations a
JOIN sessions_base sb ON sb.id = a.session_id
WHERE a.annotator = 'user'
ORDER BY a.created_at DESC;
```

### The sync lifecycle

```
1. User creates annotation via CLI or HTTP API
   → Store.AddAnnotation() → SQLite INSERT → markUnsynced()

2. User runs: go-minitrace annotate sync --output-dir ./output
   → Store.GetUnsyncedSessions() → for each session:
     → GetAnnotationsForSession()
     → SyncSession() → Read JSON → patch annotations → atomic write
     → markSynced()

3. User runs: go-minitrace validate --path ./output --recursive
   → ValidatePath() → validateAnnotations() → checks structure + categories

4. User queries via DuckDB:
   → In `go-minitrace serve`: annotations are live via sqlite_scanner → immediate results
   → In `go-minitrace query duckdb`: synced `.minitrace.json` annotations are queried from the archive
```

After the main implementation wave, three follow-up commits improved the usability story around the feature without changing the underlying storage architecture:

These follow-ups matter because the hardest part of the feature is not only storing annotations correctly, but making the write/sync/query workflow legible to a future operator or LLM agent.


These items were in the original design but not implemented in this phase:

| Item | Description | Priority |
|------|-------------|----------|
| `QueryEditor` cross-session annotation search | Search/filter sessions by annotation content in the query builder | Medium |
| `annotate get` command | Fetch a single annotation by ID (currently only session-scoped listing exists) | Low |
| `annotate stats` command | Summarize annotation counts by category, annotator, session | Low |
| `GetAnnotationByID()` in store | Single-row lookup function (currently only `List` + `GetAnnotationsForSession`) | Low |
| Pagination metadata in `List` response | Total count requires a separate `SELECT COUNT(*)` query | Low |
| `--diff` flag on sync | Show exact JSON diff before writing | Low |
| Classification de-escalation enforcement | Prevent `classification: "public"` annotation on a `classification: "internal"` session | Low |
| Transaction around `markUnsynced` | Serialize concurrent upserts for the same session_id (rare edge case) | Very low |
